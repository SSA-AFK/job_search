| 文档信息 | 内容 |

## 1. 产品概述

AI 公司检索是一套面向求职决策的公司资料检索产品。用户可以按公司名称或别名搜索企业，结合行业、细分领域、融资阶段、公司规模和所在城市缩小范围，并查看公司基本信息、公开备案、资料依据和在招职位。

当本地数据库中没有匹配公司时，系统可在管理员启用采集服务后创建资料采集任务，通过经授权的数据源收集公开资料，使用兼容 OpenAI 接口的大模型完成结构化提取、规范化和去重，最终将可验证的数据写回本地数据库。

产品采用“本地查询优先、外部采集可选”的工作模式。即使 Redis、Celery、大模型或外部数据源不可用，已经写入 SQLite 的公司与职位数据仍可正常查询。

## 2. 产品目标与边界

### 2.1 产品目标

- 帮助用户快速发现符合行业、融资阶段、规模和城市偏好的公司。
- 将公司概况、备案信息、资料来源和招聘职位集中展示，减少跨站点查找成本。
- 为关键公司字段提供来源、覆盖字段、置信度和获取时间，便于用户判断资料可信度与时效性。
- 在缺少目标公司时，通过受控的异步采集流程补充公开资料。
- 在外部服务故障时保留核心查询能力，避免采集系统故障影响已有数据使用。

### 2.2 非目标

- 不提供简历管理、职位收藏、投递进度跟踪或用户账号体系。
- 不保证覆盖全部公司、全部职位或实时招聘信息。
- 不替代工商、监管机构或招聘方发布的官方信息。
- 不自动抓取未经明确授权的网站，也不通过大模型生成或扩大网站访问白名单。
- 当前界面不提供后台配置、数据修订、采集任务管理或覆盖率报表页面。

## 3. 目标用户与核心场景

### 3.1 目标用户

| 用户角色 | 主要诉求 |
| --- | --- |
| 求职者 | 筛选目标公司，了解公司背景、在招职位和投递渠道 |
| 招聘与人才研究人员 | 按结构化条件观察公司和招聘信息，核对资料来源 |
| 产品运营人员 | 通过种子数据或采集服务维护可检索的公司资料 |
| 部署与运维人员 | 管理数据库、采集依赖、数据源授权、任务队列和系统健康状态 |

### 3.2 核心使用场景

1. 用户输入公司名称或别名，系统返回名称或别名包含关键词的公司。
2. 用户组合行业、细分领域、融资阶段、规模和城市筛选目标公司。
3. 用户进入公司详情，核对公司别名、备案登记、证据来源及更新时间。
4. 用户查看当前在招职位、职位类型、城市、薪资、发布时间和外部投递链接。
5. 用户搜索不到公司时，系统在采集功能启用的前提下自动提交补充资料请求，并持续显示任务状态。
6. 运维人员离线查看最近 24 小时职位来源覆盖情况，识别数据新鲜度和采集覆盖问题。

## 4. 用户使用流程

### 4.1 公司检索

1. 访问 `/companies` 进入公司列表页。
2. 在搜索框输入公司名称或别名；前端在停止输入 250 毫秒后更新结果。
3. 可选择行业、细分领域、融资阶段、公司规模和城市进行精确筛选。
4. 可按相关度、最近更新或公司名称排序。未输入关键词时默认按最近更新时间排序；输入关键词时默认按相关度排序。
5. 列表每页展示 20 家公司，并提供上一页、下一页和清除全部筛选条件操作。

相关度排序依次优先考虑：公司名称完全匹配、别名完全匹配、公司名称前缀匹配、别名前缀匹配、公司名称包含、别名包含。

### 4.2 查看公司详情

1. 点击公司名称进入 `/companies/{companyId}`。
2. 查看公司名称、别名、行业、细分领域、融资阶段、规模、城市、简介、官网和资料更新时间。
3. 查看备案与登记信息，包括备案类型、编号、名称、主管机构、日期、状态和详情链接。
4. 查看资料依据，包括来源渠道、来源链接、覆盖字段、置信度和获取日期。
5. 查看职位记录总数以及当前在招职位数量。

### 4.3 查看在招职位

公司详情页默认仅展示当前有效职位，每页 10 条，并按发布时间倒序排列。每条职位可展示：

- 职位名称与招聘状态；
- 职位类型，包括全职、兼职、实习、临时、校招、社招或待确认；
- 工作城市；
- 月薪下限、上限及年薪月数；
- 职位描述与发布日期；
- 一个或多个外部投递渠道。

系统只将有效的 HTTP 或 HTTPS 地址渲染为外部链接。

### 4.4 缺失公司资料采集

仅当搜索条件满足以下要求时，前端才会尝试发起采集：

- 使用了 2 至 100 个字符的公司关键词；
- 未同时使用行业、细分领域、融资阶段、规模或城市筛选；
- 本地查询结果为 0；
- 查询请求本身没有失败。

采集状态包括：提交中、排队中、采集中、部分成功、成功和失败。前端先按 2 秒、4 秒、8 秒间隔轮询，之后每 10 秒轮询一次，自动轮询最长持续 120 秒。成功且返回公司 ID 后，页面自动打开新生成或更新后的公司详情；超时后用户可手动刷新状态。

默认配置中采集功能关闭。关闭时系统明确提示采集服务暂不可用，但本地公司查询和详情浏览不受影响。

## 5. 功能说明

### 5.1 公司列表

| 功能 | 说明 |
| --- | --- |
| 关键词搜索 | 对规范化后的公司名称和别名执行包含匹配 |
| 结构化筛选 | 支持行业、细分领域、融资阶段、规模、城市 |
| 排序 | 相关度、最近更新、公司名称 |
| 分页 | 默认每页 20 条，后端最多允许每页 100 条 |
| 公司摘要 | 展示名称、城市、行业、细分领域、融资阶段、规模、简介、官网 |
| 状态反馈 | 提供加载骨架、空结果、超页、请求失败与重试状态 |
| URL 状态 | 搜索、筛选、排序和页码写入 URL，便于刷新或分享当前视图 |

当前前端预设的行业包括人工智能与互联网科技；细分领域包括基础模型、多模态模型和 AI 平台；城市包括北京、上海、杭州和深圳。后端接口可以接受其他合法的行业、细分领域和城市字符串。

### 5.2 公司详情与证据

详情页将事实数据与证据数据分开展示。公司事实包括名称、别名、分类、融资、规模、城市、简介和官网；证据数据包括公开备案以及公司资料来源。

每条资料来源包含来源渠道、原始 URL、标题、所支持的公司字段、置信度、发布时间和获取时间。该设计用于帮助用户判断“信息从哪里来、支持了哪些字段、何时获取”，而不是仅展示无法追溯的聚合结果。

### 5.3 数据采集与处理

采集链路由以下阶段组成：

1. 创建采集请求并异步派发任务。
2. 调用已启用且获得授权的数据源获取原始文档。
3. 识别与查询相符的目标公司。
4. 在网站主机名获得管理员批准时，可继续采集公司官网资料。
5. 使用大模型分别提取公司档案、职位和备案信息。
6. 验证结构化输出与证据引用关系。
7. 规范化公司名称、职位、薪资等字段，并执行公司和职位去重。
8. 在事务中写入公司、职位、来源、证据和采集运行记录。

当前生产组合支持的可选数据源为知乎全局搜索接口和管理员批准的公司官网。其他商业招聘网站或企业数据源默认不启用，必须先具备合法凭据与采集授权。

### 5.4 数据新鲜度与覆盖

系统保存职位来源、采集快照和来源生命周期信息，用于判断职位是否仍然有效。由完整快照管理的职位来源采用“连续两次完整快照缺失”规则更新状态；旧数据或仅关联部分/失败快照的数据仍使用 30 天年龄回退规则。

运维人员可运行覆盖率命令，离线读取数据库并输出最近 24 小时覆盖报告。当前该能力以命令行形式提供，不在前端展示。

## 6. 数据模型概览

| 数据对象 | 核心内容 |
| --- | --- |
| 公司 | 规范名称、行业、细分领域、融资阶段、规模、城市、官网、简介、更新时间 |
| 公司别名 | 公司历史名称、英文名、产品名或其他检索别名 |
| 备案与登记 | ICP、算法备案、企业登记及其编号、机构、日期和状态 |
| 职位 | 名称、类型、城市、薪资、描述、发布时间、有效状态 |
| 职位来源 | 数据源、原始标识、投递链接、首次/最近发现时间、有效状态 |
| 原始资料 | 来源渠道、外部标识、URL、标题、正文摘要及获取时间 |
| 公司字段证据 | 资料与公司字段之间的支持关系及置信度 |
| 采集请求与运行 | 查询词、任务状态、错误代码、尝试的数据源、文档与职位数量 |
| 覆盖快照 | 某次采集对职位集合的覆盖范围、完整性和生命周期依据 |

## 7. 状态、异常与降级

| 场景 | 产品行为 |
| --- | --- |
| 查询无结果 | 无结构化筛选时可尝试采集；否则提示调整关键词或筛选条件 |
| 公司不存在 | 详情页提示公司未收录或链接失效 |
| 公司或职位接口失败 | 保留当前页面并提供重新加载操作 |
| 采集功能关闭或配置无效 | 返回 `collection_unavailable`，本地查询继续可用 |
| 数据源超时、鉴权失败或限流 | 记录公开错误代码；有部分有效结果时可标记为部分成功 |
| 自动轮询超时 | 停止自动更新，保留请求并允许用户手动刷新 |
| Redis 缓存不可用 | 查询回退到数据库，不将缓存作为核心数据源 |
| 重复任务投递 | 通过运行状态和 claim token 避免重复写入或覆盖已完成结果 |

采集运行只保存经过清理的错误摘要，不保存凭据或原始大模型输出。

## 8. 权限、安全与合规原则

- 当前版本没有终端用户登录与角色权限系统，适合本地或受控网络环境部署；如需公网开放，应由部署层补充身份认证、访问控制和流量限制。
- 外部数据源仅在管理员显式启用并配置授权凭据后使用。
- 公司官网采集采用精确主机名白名单；请求前后均校验 HTTP(S) 目标、重定向、同源限制和 `robots.txt`。
- 官网采集单次最多访问 10 个页面，并对并发数和请求启动间隔进行限制。
- 大模型输出必须通过 JSON Schema 和证据关系校验，不能直接作为可信数据写入。
- API 密钥和数据源密钥不得写入仓库、示例配置、测试夹具或命令历史，应使用进程环境变量或合规的密钥管理服务。
- 页面仅允许 HTTP/HTTPS 外链，避免将未校验协议渲染为可点击链接。

## 9. 系统组成与运行依赖

| 层级 | 技术与职责 |
| --- | --- |
| Web 前端 | React 19、TypeScript、Vite；负责检索、筛选、详情、职位和采集状态交互 |
| API 服务 | FastAPI；提供公司、职位、采集请求和健康检查接口 |
| 数据访问 | SQLAlchemy、Alembic；负责关系模型、查询和迁移 |
| 主数据库 | 默认 SQLite；保存公司、职位、证据和采集任务，是状态事实来源 |
| 可选缓存 | Redis；用于公司列表、详情和职位查询缓存 |
| 异步任务 | Celery + Redis；执行采集任务、重试与过期任务协调 |
| AI 提取 | 兼容 OpenAI Chat Completions 的模型服务；负责结构化提取与语义去重 |
| 数据源 | 知乎授权接口、管理员批准的公司官网 |

最低开发环境要求为 Python 3.12 及以上、Node.js 20 及以上和 npm。仅使用种子数据浏览产品时，不需要 Redis、Celery、大模型凭据或外部数据源。

## 10. 对外接口概览

所有业务接口使用 `/api/v1` 前缀。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /health` | 服务健康检查 |
| `GET /companies` | 搜索、筛选、排序和分页查询公司 |
| `GET /companies/{company_id}` | 获取公司详情、备案和资料依据 |
| `GET /companies/{company_id}/jobs` | 获取公司职位，支持职位类型、城市和有效状态筛选 |
| `POST /collection-requests` | 提交公司资料采集请求 |
| `GET /collection-requests/{request_id}` | 查询采集请求状态与结果 |

公司列表默认每页 20 条，职位列表页面默认每页 10 条。采集请求关键词长度必须为 2 至 100 个字符。更完整的接口字段和校验规则以运行时生成的 FastAPI OpenAPI 文档为准。

## 11. 部署模式

### 11.1 基础查询模式

适用于演示、离线检索和已有数据浏览。只需启动 SQLite、FastAPI 和前端。`COLLECTION_ENABLED=false` 时，采集相关依赖均可不配置。

### 11.2 完整采集模式

除基础服务外，还需启动 Redis、Celery Worker 和 Celery Beat，并配置：

- `COLLECTION_ENABLED=true`；
- Celery Broker 与结果后端；
- 兼容 OpenAI 的接口地址、模型名称和 API Key；
- 至少一个获得授权且已启用的数据源；
- 官网采集启用时的精确主机名白名单。

完整采集模式下，数据库中的采集请求与运行记录仍是状态事实来源；消息队列只负责任务传递。

## 12. 当前数据与质量基线

仓库附带 5 家示例公司及其职位、来源和部分备案数据，用于本地演示和端到端验证。种子导入可重复执行，不会重复创建公司、职位或来源记录。

当前测试体系覆盖后端单元与接口测试、迁移测试、采集集成测试、前端组件测试、桌面与移动端浏览器流程，以及使用真实迁移和种子数据的端到端流程。代表性性能测试使用 10,000 家公司和 100,000 条职位数据，要求 50 次查询的 p95 不高于 300 毫秒。

## 13. 已知限制

- 前端筛选选项目前是固定预设，未从数据库动态生成。
- 搜索采用本地数据库名称与别名包含匹配，不是自然语言语义搜索。
- 当前没有用户账户、收藏、对比、导出、订阅或消息通知功能。
- 当前没有面向运营人员的数据编辑、纠错审核、来源管理和任务管理界面。
- 采集结果依赖外部数据源的授权、可用性、内容质量和大模型服务质量。
- 公司官网只有在主机名进入管理员白名单后才能采集，因此并非所有搜索缺失项都能补全。
- 覆盖率和采集运行诊断目前主要通过命令行与数据库查看。
- 产品资料用于辅助决策；涉及投递、薪资、备案和企业状态时，用户仍应访问原始来源复核。

## 14. 建议的后续演进

1. 增加运营后台，支持资料审核、纠错、合并、来源配置和采集任务诊断。
2. 将筛选项、数据覆盖率和最近更新时间做成动态可视化指标。
3. 增加公司收藏、对比、职位订阅和数据导出等求职决策工具。
4. 在合规授权前提下扩展数据源，并为各来源建立独立的质量与新鲜度指标。
5. 在公网部署前补充身份认证、权限分级、审计日志、请求限流和隐私政策。

## 15. 验收要点

- 用户可以在不配置采集依赖的情况下查询种子公司、打开详情并访问职位来源。
- 名称和别名检索、五类结构化筛选、三种排序以及分页行为符合本说明。
- 公司详情能正确展示备案、资料依据、职位总数和当前在招数量。
- 搜索无结果时，只有符合条件的纯关键词查询才会触发采集流程。
- 采集关闭时返回明确的不可用状态，且不会影响已有公司查询。
- 采集成功后自动进入公司详情；部分成功、失败和超时均有明确状态反馈。
- 所有外部链接均经过 HTTP/HTTPS 协议校验。
- 种子数据重复导入保持幂等，数据库迁移、后端测试、前端测试和构建检查通过。
