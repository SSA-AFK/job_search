# 外部职位数据源枚举设计

## 1. 背景与目标

招聘入口 URL 验证阶段只负责确认公司是否有公开、可信的招聘入口，不抓取职位。职位枚举作为独立后续阶段，仅在数据库职位数据需要更新时运行。

本阶段不再为每个 ATS 或招聘网站开发和维护平台专属提取器，而是使用两个边界清晰的外部工具：

- JobHunt-CLI：面向其明确支持的公司，从公开招聘官网读取结构化职位。
- boss-zhipin-scraper：用户人工登录隔离 Chrome 后手动运行，用于批量补充未被 JobHunt-CLI 覆盖的公司。

目标是在可控维护成本下获得职位数据，同时避免为每家公司遍历全部渠道、自动处理登录态或持续适配易变页面。

## 2. 与入口验证阶段的关系

入口验证和职位枚举是两个独立阶段：

1. 入口验证阶段产出一个 `verified` 招聘入口 URL，或稳定的未验证结果。
2. 职位枚举阶段消费已知公司身份和已有数据库状态，并按明确的数据源能力路由。

职位枚举不得重新引入逐 ATS 域名搜索、平台 DOM 解析或多 Provider 试错。JobHunt-CLI 可以在公司没有已验证入口时提供官方职位数据，但其结果不能反向把任意 URL 标记为已验证入口，除非该 URL 单独通过入口验证规则。

## 3. 触发条件

收到公司名时，系统首先解析为标准公司身份并查询数据库：

1. 若存在未过期的可用职位数据，直接读取数据库，不调用外部工具。
2. 若职位数据不存在或已过期，检查公司是否映射到 JobHunt-CLI 支持的站点。
3. 只有映射明确时才创建 JobHunt-CLI 枚举任务。
4. JobHunt-CLI 不支持或枚举失败时，记录状态并停止，不自动回退 BOSS。
5. BOSS 数据只能通过用户手动发起的独立批量导入流程进入系统。

默认新鲜期为 24 小时。新鲜期应作为单一配置项存在，不允许按平台增加独立策略；后续只有在观测数据证明必要时才调整。

## 4. 数据源路由

路由依据是数据源是否明确支持目标公司，而不是“大厂”或“中小厂”标签。

| 条件 | 动作 |
| --- | --- |
| 数据库职位在新鲜期内 | 直接返回数据库结果 |
| JobHunt-CLI 明确支持该公司 | 只调用 JobHunt-CLI |
| JobHunt-CLI 不支持该公司 | 不自动抓取；保留已验证入口 |
| JobHunt-CLI 调用失败 | 记录失败；不自动回退 BOSS |
| 用户提供人工 BOSS 批次 | 校验并批量匹配公司后导入 |

同一次自动枚举任务只允许一个外部职位数据源。

## 5. JobHunt-CLI 主数据源

### 5.1 能力发现与公司映射

- 使用固定版本的 `job sites --format json` 获取工具明确支持的站点。
- 将本系统公司 ID 映射到 JobHunt-CLI 的稳定站点键。
- 映射必须来自明确配置或经过审核的别名，不得仅靠模糊名称猜测。
- 一个站点键只能映射到一个标准公司；存在歧义时停止并进入人工复核。

### 5.2 调用方式

- JobHunt-CLI 作为隔离的外部进程运行，通过 JSON 输入输出边界接入。
- 固定 npm 包版本或固定仓库提交，不在运行时执行 `job update` 或 `npx` 的隐式最新版安装。
- 使用无交互命令并设置超时、输出大小和最大职位数量。
- 社招、校招、实习可以在一次受控任务内按该站点声明的能力查询，但不得探测未声明支持的类型。
- 原始 stderr 仅进入受限诊断日志，不能直接作为公开错误信息。

### 5.3 输出校验

每条职位至少需要：

- 稳定的站点键与职位 ID；
- 职位名称；
- 公开详情 URL；
- 招聘类型；
- 来源时间或本次观察时间。

城市、部门、更新时间、职责和任职要求为可选字段。所有 URL 仍需通过本系统的安全和允许域检查。结构不合法的记录单条拒绝；当拒绝比例超过 20% 时，整个批次标记为失败，不写成功完整快照。

### 5.4 许可证门槛

正式分发、复制或修改 JobHunt-CLI 代码前，仓库必须提供可核验的许可证文件。仅在 `package.json` 声明 `MIT` 而仓库缺少许可证正文时，不复制其源码进入本仓库。

在许可证文件补齐前，只允许以下模式：

- 用户自行安装固定版本的外部 CLI；
- 本系统通过进程边界调用；
- 本系统不打包、不镜像、不重新分发该工具源码或 npm 包。

## 6. BOSS 人工补充通道

### 6.1 触发边界

- 只能由用户在本地明确发起。
- 必须使用 boss-zhipin-scraper 自己的隔离 Chrome profile。
- 首次和登录失效后由用户手动完成 BOSS 登录。
- 不进入 Celery、定时任务、后台自动重试或无人值守流程。
- 不复制用户主 Chrome profile，不读取或转移其通用浏览器凭据。
- 不作为 JobHunt-CLI 失败后的自动回退。

### 6.2 批量而非逐公司抓取

BOSS 工具按职位关键词、城市和有限页数运行，其输出天然是跨公司结果。因此一次人工运行形成一个导入批次，而不是为每家公司单独运行。

批次必须记录：

- 工具版本；
- 查询关键词、城市和页数；
- 执行时间；
- 原始输出文件指纹；
- 解析、接受、拒绝和待复核数量。

### 6.3 公司匹配

只有以下强证据可自动匹配到公司：

- 已审核的 BOSS 品牌 ID 与本系统公司 ID 映射；
- 完全匹配的标准名称或已确认别名，同时不存在同名歧义；
- 已有人工确认的来源映射。

模糊名称、简称冲突、集团与子公司不清等情况进入人工复核，不得自动写入职位。未匹配记录保留在导入批次中，不创建新公司。

### 6.4 合规与风控

- 工具的登录态、请求预算、访问限制和用户协议风险由人工操作者显式确认。
- 系统不得增加验证码规避、代理轮换、指纹伪装或自动登录能力。
- 遇到登录墙、验证码、环境异常或访问频繁时立即停止当前人工批次。
- 不把 BOSS 数据用于商业转售，正式运营前应完成适用用户协议和法律审查。

## 7. 通用导入边界

两个外部工具都转换为同一内部候选契约：

- `source_provider`
- `source_raw_id`
- `company_id`
- `title`
- `apply_url`
- `job_type`
- `city`
- `department`
- `description`
- `requirements`
- `observed_at`
- `source_payload_hash`

适配器只负责调用工具、校验 JSON 和转换字段。现有持久化层负责归一化、精确来源去重、职位合并和快照写入。不得把两个开源项目的内部数据模型传播到业务层。

## 8. 快照与生命周期

### 8.1 JobHunt-CLI

只有同时满足以下条件时，才能写入完整成功快照：

- 工具命令成功退出；
- 请求的招聘类型全部完成；
- 工具明确完成分页或达到其声明的结果总数；
- 输出校验通过且拒绝比例不超过阈值；
- 没有截断、超时、限流或来源错误。

否则只能写 `partial` 或 `failed` 快照，不能关闭旧职位。确认完整的零职位结果才能写可信空快照。

### 8.2 BOSS

BOSS 人工查询是关键词和城市范围内的抽样，不代表公司完整职位列表。其批次永远不能产生公司级完整快照，也不能用于关闭旧职位；它只能新增或刷新实际观察到的职位来源。

## 9. 状态与失败处理

稳定状态至少包括：

- `fresh_database_hit`
- `source_unsupported`
- `source_succeeded`
- `source_partial`
- `source_failed`
- `manual_import_pending_review`
- `manual_import_completed`

稳定失败代码包括：

- `jobhunt_not_installed`
- `jobhunt_version_mismatch`
- `jobhunt_site_unmapped`
- `jobhunt_timeout`
- `jobhunt_invalid_output`
- `jobhunt_source_unavailable`
- `boss_login_required`
- `boss_access_blocked`
- `boss_company_unmatched`
- `manual_import_invalid`

失败不得触发另一数据源。读取已有数据库职位不因外部更新失败而中断。

## 10. 性能与预算

- 新鲜数据命中时外部请求为 0。
- 单家公司自动更新只启动一个 JobHunt-CLI 进程。
- 同一公司在已有进行中的更新任务时不得重复调度。
- JobHunt-CLI 设置最大运行时间和最大输出记录数；超限为 partial 或 failed。
- BOSS 一次人工批次可包含多家公司，但页数、城市和关键词由用户显式指定并受工具本身上限约束。
- 禁止逐公司自动运行 BOSS。

## 11. 现有代码处理

从生产职位枚举调用链中移除或停用：

- 飞书、Moka、字节跳动、BOSS、猎聘和拉勾的独立列表提取器；
- ATS Playwright 列表渲染与滚动；
- 自动 BOSS CDP Provider；
- 逐平台 ATS 搜索循环；
- LLM 职位列表抽取；
- 在入口发现期间直接写职位的路径。

保留：

- 公司身份和别名体系；
- `JobEntry`、`JobPosting`、`JobSource` 和职位快照模型；
- 归一化、去重、持久化与完整快照生命周期规则；
- 数据库优先的查询 API；
- URL 安全校验和可观测诊断。

删除源文件前必须确认没有其他已批准调用方，并严格核对工作区状态，不得删除或覆盖用户未提交改动。

## 12. 测试

### 12.1 JobHunt-CLI 适配器

- 固定版本检查通过与失败。
- 支持站点发现和唯一公司映射。
- 超时、非零退出、过大输出和非法 JSON。
- 单条无效记录与超过 20% 拒绝阈值。
- 招聘类型和 URL 安全验证。
- 完整、部分、失败和可信空快照映射。

### 12.2 BOSS 导入

- 只有手动入口可以创建批次。
- 品牌 ID、精确名称和别名强匹配。
- 同名、模糊名称和集团子公司进入复核。
- 批次重复导入保持幂等。
- BOSS 批次不产生完整快照、不关闭旧职位。
- 登录或风控错误终止批次且不触发自动重试。

### 12.3 编排与回归

- 新鲜数据库命中不调用外部进程。
- JobHunt-CLI 不支持或失败时不调用 BOSS。
- 同一公司不会并发启动重复更新。
- 公司查询在更新失败时仍返回已有职位。
- 入口 URL 验证阶段不调用两个职位枚举工具。
- 默认测试不访问真实招聘网站、不启动 Chrome，也不安装 npm 包。

## 13. 验收标准

- 从公司名到职位数据只有一次能力路由，不遍历全部渠道。
- 新鲜职位数据直接从数据库返回。
- 自动路径中每家公司至多调用一个外部工具。
- BOSS 仅能人工批量触发，且永不自动回退。
- 未覆盖公司安全停止并保留已验证招聘入口，不新增平台提取器。
- JobHunt-CLI 与 BOSS 输出均经过统一契约、公司身份校验和持久化规则。
- 只有真正完整的 JobHunt-CLI 枚举可以驱动职位关闭；BOSS 永远不能。
