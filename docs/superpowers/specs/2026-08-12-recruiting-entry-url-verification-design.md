# 招聘入口 URL 轻量验证设计

## 1. 背景

现有职位采集流程把招聘入口发现、URL 验证、职位列表渲染、平台解析、职位持久化和覆盖快照写入放在同一次公司采集运行中。为提高覆盖，流程会按多个 ATS 域名重复搜索，并为飞书、Moka、BOSS、猎聘、拉勾和字节跳动维护独立提取逻辑。

这种策略使单家公司产生多轮外部请求和平台试错。新增平台还需要独立适配页面结构，成本与实际得到的稳定数据不成比例。

本阶段收缩为一个目标：用有限成本确认某家公司是否存在一个公开、可访问且归属可信的招聘入口 URL。

## 2. 范围

### 2.1 本阶段交付

- 为已知公司选择并验证至多一个招聘入口 URL。
- 优先复用数据库中的已有入口，其次检查公司官网，最后至多调用一次搜索服务。
- 对每家公司执行严格的候选数、搜索次数和 HTTP 请求预算。
- 第一个候选验证通过后立即停止，不继续尝试其他来源。
- 保存验证状态、最终 URL、检查时间和稳定失败原因。
- 保留现有公网地址、SSRF、重定向和 robots 安全边界。

### 2.2 不在本阶段

- 职位列表抓取、滚动、分页和完整性判断。
- 职位详情抓取和字段补全。
- 职位解析、去重、写入和职位生命周期更新。
- 成功、空列表或部分职位列表快照。
- 为 ATS 或招聘网站维护独立列表提取器。
- 使用 LLM 解析职位内容。
- 通过登录态、CDP、验证码规避或其他增强通道访问招聘网站。

URL 可用但无法读取职位列表仍属于本阶段成功，不得降级为入口失败。

## 3. 设计原则

1. **先验证入口：** 本阶段不把职位数量作为入口可用性的条件。
2. **成功即短路：** 一旦得到 `verified` 结果，立即结束该公司的入口处理。
3. **硬预算：** 达到预算时停止，不追加兜底渠道。
4. **通用验证：** URL 验证器不包含平台专属职位 DOM 选择器。
5. **结果可解释：** 失败必须归入稳定、有限的原因集合。
6. **安全不降级：** 精简功能不得删除 SSRF、重定向、robots 或授权域名检查。

## 4. 候选来源与顺序

每家公司严格按以下顺序处理：

1. 数据库中已保存的招聘入口 URL。
2. 已验证公司官网中直接发现的招聘链接。
3. 一次搜索服务请求返回的候选 URL。

同一规范化 URL 只验证一次。候选按来源优先级和已有置信度排序，不为提高覆盖而遍历所有 Provider 或逐个 ATS 域名搜索。

官网阶段只检查首页及其直接招聘链接，不进行站点爬取。搜索阶段使用一条通用公司招聘查询，不生成 `site:jobs.feishu.cn`、`site:app.mokahr.com` 等平台枚举查询。

## 5. 硬预算

单家公司单次运行的上限为：

| 项目 | 上限 |
| --- | ---: |
| 搜索服务调用 | 1 次 |
| 进入验证的不同候选 URL | 3 个 |
| 入口流程发出的 HTTP 请求 | 5 次 |
| 验证成功后继续请求 | 0 次 |

robots 请求和重定向请求计入 HTTP 请求预算。预算耗尽后保存 `budget_exhausted`，不得自动启用浏览器渲染、其他搜索 Provider 或平台提取器。

## 6. URL 验证器

通用验证器接收公司身份信息和一个候选 URL，返回一个结构化验证结果。

### 6.1 安全和访问检查

- 只允许无用户信息的 HTTP/HTTPS URL。
- 初始地址、每次重定向和最终地址都必须通过公网 IP 与允许域检查。
- 遵守现有 robots 策略。
- 拒绝登录页、验证码、访问封禁、404 和通用错误页。
- 响应体必须受现有大小和超时限制约束。

### 6.2 招聘语义检查

以下信号可共同证明页面是招聘入口，但任何单个弱信号都不能单独通过验证：

- URL 路径包含稳定的招聘语义，如 `career`、`careers`、`job`、`jobs`、`position` 或对应中文语义。
- 页面标题或正文包含招聘、职位、加入我们等语义。
- 页面包含指向职位、职位分类或申请动作的公开链接。

验证器只判断招聘入口语义，不提取职位记录。

### 6.3 公司归属检查

满足以下任一强证据时可确认归属：

- 候选位于已验证公司官网域名内。
- 官网直接链接到候选 ATS URL，且链接关系在当前运行内经过安全请求验证。
- 页面标题、正文或结构化元数据包含公司的规范名或已确认别名，并达到现有身份匹配阈值。
- 数据库中已有经过人工或可信证据确认的公司与入口绑定。

仅凭候选 URL 位于知名 ATS 域名不能确认公司归属。

## 7. 状态模型

验证结果仅包含三种业务状态：

| 状态 | 含义 | 是否保存为可用入口 |
| --- | --- | --- |
| `verified` | 地址公开可访问，招聘语义和公司归属均通过 | 是 |
| `unverified` | 页面可访问，但招聘语义或公司归属证据不足 | 否 |
| `unavailable` | 地址失效、被阻断、违反安全策略或无法访问 | 否 |

失败原因使用有限的稳定代码：

- `not_found`
- `unsafe_url`
- `robots_disallowed`
- `request_timeout`
- `access_blocked`
- `login_required`
- `not_recruiting_page`
- `company_ownership_unverified`
- `budget_exhausted`
- `provider_unavailable`

底层异常详情不得成为公开错误码，也不得包含密钥、完整响应正文或浏览器状态。

## 8. 数据流

1. 加载公司身份、别名、官网和现有招聘入口。
2. 建立有序且去重的候选队列。
3. 取下一个候选并检查预算。
4. 调用通用验证器。
5. 若为 `verified`，更新或创建公司入口，记录检查时间并立即结束。
6. 若为 `unverified` 或 `unavailable`，保存入口级诊断并处理下一个候选。
7. 本地候选耗尽且尚未搜索时，至多执行一次通用搜索并加入候选。
8. 候选耗尽或预算耗尽后，以最具体的稳定原因结束。

该流程不得调用职位提取器、职位持久化服务或职位覆盖快照服务。

## 9. 现有组件处理

### 9.1 保留

- `JobEntry` 作为公司招聘入口记录。
- URL 规范化和公司身份匹配能力。
- 安全 HTTP 客户端、DNS/公网地址验证、重定向复检和 robots 策略。
- 一个搜索 Provider，且仅在本地候选无法验证时调用一次。
- collection run 的状态和诊断记录能力。

### 9.2 从本阶段运行时移除或停用

- ATS 列表 Provider 及飞书、Moka、字节跳动、BOSS、猎聘、拉勾列表提取器。
- Playwright ATS 渲染、自动滚动和等待职位选择器。
- BOSS CDP 公司职位 Provider。
- `_ATS_DISCOVERY_TERMS` 式逐平台搜索循环。
- LLM 职位抽取与列表页面通用职位解析。
- `DirectAtsPersistence` 的职位和职位快照写入路径。

若这些组件还被其他已批准阶段使用，可以保留源文件，但必须从本阶段的生产组合与调用链中断开。确认无调用方且测试迁移完成后才删除文件，删除前必须核对工作区范围并避免影响用户未提交改动。

## 10. Collection run 语义

- 找到 `verified` 入口：run 为 `succeeded`。
- 未找到可验证入口，但流程按预算正常完成：run 为 `partial`，并保存最具体的失败原因。
- 安全基础设施、数据库或唯一搜索 Provider 不可用且无法继续：run 为 `failed` 或沿用现有可重试基础设施语义。
- `jobs_found` 和 `jobs_written` 在本阶段恒为 0。
- run 成功不代表存在任何已采集职位，也不创建成功或空职位列表快照。

## 11. 测试与验收

### 11.1 单元测试

- 初始 URL、每次重定向和最终 URL 均执行安全验证。
- 登录、验证码、404、封禁和通用错误页得到稳定状态与错误码。
- 招聘语义充分但公司归属不足时返回 `unverified`。
- 官网直链、可信既有绑定和名称证据可以确认归属。
- URL 规范化去重防止同一候选重复请求。
- 第一个候选通过后不再调用任何 Provider。
- 请求、候选和搜索预算分别达到上限时立即停止。

### 11.2 编排测试

- 已有入口可用时不访问官网发现或搜索服务。
- 官网发现入口可用时不调用搜索服务。
- 搜索服务每家公司至多调用一次。
- 不再生成逐 ATS 域名查询。
- 入口流程不调用职位解析、职位持久化或职位快照服务。
- 所有结束路径的 `jobs_found` 和 `jobs_written` 均为 0。

### 11.3 回归测试

- 公司搜索和详情仍能读取已有职位数据。
- 旧职位数据不会因为入口验证失败而失活或删除。
- Redis、Celery、搜索服务或外部网络不可用时，现有数据库读取功能不受影响。
- 默认测试不得访问真实网络、浏览器或外部模型。

### 11.4 验收标准

- 任一家公司不会遍历所有招聘渠道。
- 单次运行严格满足 1 次搜索、3 个候选和 5 次 HTTP 请求上限。
- `verified` 后没有额外外部请求。
- 生产入口验证链路中不存在平台专属职位提取或职位写入。
- 每个非成功结果都有一个稳定、可观测且不泄露敏感信息的原因。

## 12. 后续阶段边界

职位列表枚举如需恢复，必须作为独立阶段设计。它只能消费已经 `verified` 的入口，并需要单独证明平台收益、分页完整性和维护成本。不得通过扩展本阶段验证器重新引入平台 DOM 解析或职位持久化。
